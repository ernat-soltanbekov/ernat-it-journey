## Root Cause

The system violated Read-After-Write consistency guarantees.

Writes were committed on the primary node while subsequent reads were routed to asynchronous replicas that had not yet replayed the required WAL records.

Replication lag created a temporary inconsistency window where users could observe stale data.

Long-running read queries on replicas caused recovery conflicts, delaying WAL replay and increasing lag.

## Technical Concepts

### Streaming Replication

PostgreSQL replicas continuously replay WAL generated by the primary node.

Replication is asynchronous by default and does not guarantee immediate visibility of newly committed data.

### Read-After-Write Consistency

Users expect recently written data to be visible immediately.

Asynchronous replicas cannot guarantee this behavior without additional routing logic.

### Recovery Conflicts

When WAL replay requires modifying data currently used by active read queries, PostgreSQL cancels those queries to preserve replication progress.

### WAL Replay Lag

Replication delay appears when WAL generation exceeds replay capacity or when replay is blocked by long-running queries.
